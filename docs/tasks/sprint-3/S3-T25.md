# S3-T25: Student Preferences Backend

## Description

Implement backend persistence for student study preferences using NestJS and Prisma.

Students should be able to retrieve and update their study preferences, including daily study limits, session lengths, available weekdays, and available study hours.

## Acceptance Criteria

- [ ] AC1: The database stores study preferences associated with a student.
- [ ] AC2: An authenticated student can retrieve their saved preferences through a GET endpoint.
- [ ] AC3: An authenticated student can create or update their preferences through a PUT endpoint.
- [ ] AC4: The backend rejects invalid study durations, empty weekday selections, and invalid time ranges.
- [ ] AC5: Students cannot access or modify another student's preferences.
- [ ] AC6: Automated tests cover preference retrieval, updates, validation, and user isolation.

## Implementation Plan

1. Extend the Prisma schema with a StudentPreferences model.
2. Create a Prisma migration.
3. Implement a NestJS preferences module, controller, and service.
4. Add request validation.
5. Associate preferences with the authenticated user.
6. Implement automated backend tests.

## Testing

- Unit tests for preference retrieval and updates.
- Validation tests for invalid inputs.
- Authorization tests for user isolation.
- Database integration testing where feasible.

## Dependencies

- Existing Prisma database integration.
- Existing authentication infrastructure.
- S3-T24 frontend preference types.

## Out of Scope

- Frontend-to-backend API integration.
- Scheduling algorithm changes.
- Google Calendar synchronization.
